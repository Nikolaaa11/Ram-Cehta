Dump completo del proyecto viejo

✓

Mientras vos llenás el formulario, yo ejecuto en mi máquina:

bash · mi terminal 
# Dump completo del proyecto viejo (us-east-1)
pg_dump "$DATABASE_URL_VIEJO" \
  --clean --if-exists --no-owner --no-acl --no-comments \
  --schema=core \
  --schema=auth \
  --schema=public \
  --schema=audit \
  --schema=app \
  --exclude-schema=storage \
  --exclude-schema=realtime \
  --file=ram-cehta-dump-YYYYMMDD-HHMM.sql

Esto genera un archivo SQL con todo el contenido:

  • 📊 10 empresas (AFIS, CEHTA, CENERGY, CSL, DTE, EVOQUE, FIP_CEHTA, REVTECH, RHO, TRONGKAI)
  • 👥 45 usuarios + 72 roles activos
  • 📒 212 cuentas del plan contable
  • 📝 56+ vouchers con sus líneas, firmas y attachments references
  • ⚖️ 10 reglas de aprobación
  • 📜 Audit log completo (cada cambio, IP, timestamp)
  • 🔄 5 migraciones SQL aplicadas (R115, R117, R123, R124, R126)
🔒 Tu data está segura

El dump corre en mi máquina con TU connection string. El archivo .sql NO se sube a ningún lado — solo lo uso para restaurar al proyecto nuevo en el Paso 5. Después se borra de mi máquina al final del proceso.

Aplicar nuevas credenciales en Fly

✓

Este es el momento crítico. Vas a redirigir el backend en producción a la DB nueva con un solo comando. Fly hace restart automático y en 60-90s el sistema está hablando con Brasil.

  1. Abrí PowerShell en cualquier carpeta
  2. Verificá que estás autenticado en Fly
    PowerShell 
    fly auth whoami

    Si responde tu email → continuá. Si dice "Not logged in" → corré fly auth login primero.

  3. Ejecutá este comando con TUS valores reales (reemplazá los placeholders en naranja):
    PowerShell · fly secrets set 
    fly secrets set `
  DATABASE_URL="<Pooler DB URL del Paso 4 — #6>" `
  SUPABASE_URL="<Project URL del Paso 4 — #1>" `
  SUPABASE_ANON_KEY="<anon key del Paso 4 — #2>" `
  SUPABASE_SERVICE_ROLE_KEY="<service_role del Paso 4 — #3>" `
  SUPABASE_JWT_SECRET="<JWT Secret del Paso 4 — #4>" `
  -a cehta-backend
    💡 Sintaxis PowerShell

    El backtick ` al final de cada línea es continuación (equivale al \ de bash). Las comillas dobles son obligatorias porque las URLs y keys tienen caracteres especiales (=, ?, +, etc.) que PowerShell interpretaría mal sin ellas.

  4. Verificá que se aplicaron
    PowerShell 
    fly secrets list -a cehta-backend

    Los 5 que cambiamos deberían decir CREATED AT: Just now.

  5. Esperá el restart automático

    Fly reinicia las 16 machines en ~60-90 segundos. Verás output tipo:

    output esperado 
    Released v124 to cehta-backend
Updating 16 machines...
Machine 18509ddb11d1d8: stopping... starting...
...
Machine 287e360f6d9258: stopping... starting...
✓ All machines updated
  6. Health check final
    PowerShell 
    curl https://cehta-backend.fly.dev/api/v1/health
    ✓ Respuesta esperada

    {"status":"ok","database":"ok"}

    Si ves esto → el backend ya está conectado a la DB de Brasil. 🇧🇷

    🚨 Si responde "degraded" o "database: down"

🛠 Troubleshooting

Si algo sale mal en algún paso, buscá acá primero.

El dropdown de region no muestra "South America (São Paulo)"

Supabase a veces oculta opciones según el plan. Verificá:

1. Que estés en Free tier o Pro (no Enterprise legacy con regiones limitadas).

2. Que el browser no esté bloqueando algún recurso de Supabase (desactivá ad-blocker temporalmente).

3. Probá en una pestaña incógnita.

fly secrets set falla con "Error: failed to update app secrets"

Causa más común: token Fly expirado o app name mal escrito.

Solución:

1. fly auth login de nuevo.

2. Verificar que la app se llama exactamente cehta-backend: fly apps list

3. Reintentar el fly secrets set.

El health check dice "database: down" después del Paso 7

Hay 3 causas posibles:

A. La connection string tiene [YOUR-PASSWORD] literal (no reemplazado por la DB password real). Más común.

B. Estás usando la direct URL (puerto 5432) en lugar de la pooler URL (puerto 6543). Producción usa pooler.

C. El IP de Fly São Paulo no está whitelisteado en la DB nueva. Por default Supabase permite todo, pero si activaste IP allowlist tenés que agregarlo.

Avisame y miro logs juntos: fly logs -a cehta-backend

Después del login, sale "JWT validation failed"

El SUPABASE_JWT_SECRET en backend no coincide con el del proyecto nuevo.

Verificá en Supabase Dashboard → Settings → API → JWT Settings → "Reveal" del JWT Secret y comparalo contra el valor que pusiste en fly secrets list.

Si difieren: fly secrets set SUPABASE_JWT_SECRET="..." -a cehta-backend

Los usuarios no pueden loguear con su password vieja

Esto es esperado. Cuando cambia el JWT secret, todas las sesiones se invalidan. Pero los passwords en la tabla auth.users siguen siendo válidos — los users pueden usar el mismo password de antes.

Si el password no funciona: usá "Olvidé mi contraseña" en el login. Se manda email de reset desde el proyecto nuevo.

Si nadie recibe el email de reset: hay que configurar SMTP en el proyecto nuevo (Settings → Auth → Email Templates). Por default Supabase usa su propio SMTP que tiene rate limit de 3 emails/hora — para uso normal alcanza.

Los integrity counts NO coinciden entre proyecto viejo y nuevo

Esto NO debería pasar con pg_dump --single-transaction. Si pasa:

1. Comparar tabla por tabla cuál difiere.

2. Si la tabla con diff es audit.action_log, puede ser que durante el dump alguien generó nuevos audit logs. No crítico.

3. Si la tabla con diff es core.vouchers o similar, hay problema serio. Abortamos y restauramos del backup del Paso 1.

Quiero abortar la migración a mitad del proceso

Depende del paso donde estés:

Antes del Paso 7 (vos no hiciste fly secrets set todavía): la app sigue 100% funcional contra la DB vieja. No hiciste cambios en producción. Solo eliminás el proyecto nuevo de Supabase y listo.

Después del Paso 7: hacé rollback del fly secrets set con las credenciales viejas (las que están en backend/.env antes de los cambios míos del Paso 6). Esto restaura producción a la DB vieja en 60-90s.

El proyecto nuevo en Brasil queda creado pero sin uso — lo pausás o eliminás.
