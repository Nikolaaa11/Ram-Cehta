2Por qué dura años

Tres capas físicamente desacopladas.

Si Vercel sube precios el doble, migrás a Netlify en 1 hora. Si Fly.io se cae, el frontend sigue dando datos cacheados. Si querés cambiar Supabase por una DB privada en 5 años, no toca el frontend. Esto es lo que se llama resiliencia arquitectónica — y es lo que separa un sistema de proyecto vs. un sistema institucional.

F

Frontend

Reemplazable. Next.js es estándar industria. Cualquier dev Next puede tomarlo. Si mañana React muere (no va a pasar), se migra a Svelte/Vue sin tocar la lógica del negocio porque toda la lógica vive en el backend.

→ Bus factor: resuelto.

B

Backend

El cerebro. FastAPI + Python es el stack más común del mundo financiero. Las reglas de negocio están en Pydantic — autodocumentadas, tipadas, testeadas. Si querés migrarlo a Rust/Go por performance en 5 años, los contratos REST quedan igual.

→ 1.108 tests blindan refactor.

D

Datos

Inmortal. Es Postgres puro — el estándar SQL más portable. Si Supabase desaparece, se exporta y se carga en RDS/CloudSQL/self-hosted en horas. Los triggers de partida doble seguirán funcionando idénticos.

→ Postgres existe desde 1996. No se va a ir.

3La unidad mínima

Todo el sistema gira alrededor del voucher.

Una factura no es un objeto. Un pago no es un objeto. Una boleta no es un objeto. Solo el voucher. Cada transacción es un voucher con líneas que cuadran. Esto es lo que permite que tu sistema sea contablemente auditable a cualquier nivel — incluso SVS.

La regla más importante: partida doble en 3 capas

Cualquiera de las 3 capas rechaza un voucher descuadrado. Si Zod (navegador) falla por bug, Pydantic (API) lo agarra. Si Pydantic falla, el trigger Postgres lo agarra. Es físicamente imposible que un asiento descuadrado llegue a la DB.

3 capas de validación · partida doble

Cómo se ve un voucher cuadrado

Ejemplo: pago a proveedor por servicios profesionales — $1.190.000 + IVA. Tres líneas, tres cuentas distintas, suma debe = suma haber.

DEBE (Activo / Gasto sube)
Gasto Servicios$ 1.190.000
IVA Crédito Fiscal$ 226.100
Total Debe$ 1.416.100
HABER (Activo / Pasivo baja)
Banco Estado · CC 1234$ 1.416.100
——
Total Haber$ 1.416.100
✓ Cuadrado · diferencia $ 0 · APROBADO por las 3 capas
4Ciclo de vida

El voucher tiene 7 estados. Solo avanza.

Nunca retrocede. Cada transición queda registrada con timestamp + usuario. Esto es lo que permite reconstruir auditablemente la historia completa de cada peso del fondo, hasta su origen, varios años después.

Draft
Libre. Permitido descuadrar mientras editás.
Pending
Cuadra. Esperando firma(s).
Approved
Firmado. Listo para ejecutar.
Executed
La plata se movió. Banco confirmó.
Synced
Cargado en Nubox (libro oficial).
Reconciled
Coincide con cartola bancaria.
Closed
Mes cerrado. Inmutable.

Estados terminales fuera de línea principal: REJECTED (no aprobado) · VOID (anulado pre-ejecución) · REVERSO (contra-asiento de uno EXECUTED)

7Longevidad

Está diseñado para durar 10 años.

No es un pitch — es una decisión arquitectónica deliberada. Cada uno de estos pilares está pensado para sobrevivir a los cambios típicos que matan sistemas financieros: rotación de personal, cambios regulatorios, crecimiento del fondo, muerte de proveedores, auditorías intensas.

Hoy → Año 1

1.108 tests automatizados

Cualquier cambio futuro que rompa una regla contable lo agarra el CI antes de mergear. Es como un auditor 24/7 que nunca duerme. La regla: no se mergea código con tests rotos.

Año 1 → Año 3

22 invariantes en SUPER_PROMPT_MAESTRO

Reglas no-negociables documentadas. Si en 2 años entra un dev nuevo y quiere "optimizar" la partida doble, lee el documento y entiende por qué no se toca. Es el contrato técnico-legal del sistema.

Año 2 → Año 5

Triggers en SQL (no solo en código)

Las reglas críticas están también en la base. Si en 5 años se reescribe todo el backend, los triggers Postgres siguen ahí defendiendo la partida doble. Hasta que alguien explícitamente los borre — y eso queda en audit log.

Año 3 → Año 7

Audit log inmutable

Cada cambio queda registrado con timestamp + usuario + IP + acción anterior + acción nueva. Cuando vengan SVS o un auditor externo en 5 años a preguntar "¿quién aprobó este pago de $50M en 2026?", la respuesta es trivial.

Año 5 → Año 10

Postgres puro · sin lock-in

Toda la lógica de datos está en SQL estándar. Si Supabase desaparece, RDS/Aurora/CloudSQL/self-hosted reciben el dump y arranca en horas. Si FastAPI muere (no va a pasar), el contrato REST documentado deja migrar a otro stack sin romper el frontend.

Siempre

Cifrado Fernet en credenciales sensibles

Las API keys de Nubox, SII, Previred, bancos están cifradas con clave que solo conoce Fly.io. Si la DB se filtra, las credenciales son binario inservible. Conformidad con regulación financiera chilena básica.

10Próximas mejoras

Lo que viene después.

Una vez en marcha blanca, las 3 mejoras de mayor impacto operativo. Acá la diferencia entre "el sistema funciona" y "el sistema es un placer usar todos los días".

⚡

Transaction pooler

Hoy backend abre conexión nueva por request → 80-200ms latencia extra. Con pgbouncer transaction pooler (free en Supabase) las conexiones se reusan.

Ganancia: 30-40% más rápido. Costo: 2 horas.

📊

Materialized views EEFF

Reportes financieros se calculan en vivo desde millones de líneas. Con MV refresh cada 5 min, abren al instante.

Ganancia: 8s → 200ms. Costo: 4-6 horas.

🤖

IA extract contratos

Claude lee facturas. Próximo nivel: que lea contratos de proveedores y precargue plantillas mensuales recurrentes ("arriendo $X cada día 5").

Ganancia: -40% tiempo data entry. Costo: 2 semanas.

⌨️

Atajos teclado + ⌘K palette

N nuevo voucher · A aprobar · ⌘K paleta tipo Linear. Productividad +30%.

Ganancia: power users felices. Costo: 3 días.

📱

PWA + push notifications

App instalable en celular. Notificación push cuando hay voucher esperando tu firma. Aprobaciones de 6h a 30 min.

Ganancia: ciclo de aprobación 10x más rápido. Costo: 1 semana.

🔍

Anomaly detection IA

Cada noche Claude analiza patrones: "este proveedor cobra siempre $400k, hoy facturó $4M", "doble pago detectado". Previene 80% de fraudes/errores.

Ganancia: red de seguridad pasiva. Costo: 1 semana.
